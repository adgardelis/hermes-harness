# HERMES HARNESS public benchmarks (issue #1)

Reproducible, offline, synthetic-data benchmark of the capability-spill
mechanism in Hermes Agent's `tools/tool_result_storage.py` at the pinned
upstream commit `49b044a322b5a87e4f45fb18e73d09d0b204165e`.

## What it measures

Per workload × per context-window profile:

- model-facing input characters before vs. after persistence;
- end-to-end persist latency, raw spill-write latency, resolve latency
  (median of 3 timed repetitions);
- exact round-trip recovery fidelity (byte equality after decrypt + digest
  verification);
- head/tail sentinel survival in the inline preview, and recovery of the
  omitted middle;
- cross-session denial of the recovery capability;
- turn-budget behavior for the multi-tool workload;
- provider cache telemetry: **N/A offline** (schema below).

## Reproduce

Requirements: Python 3.11+ and the `cryptography` package (the only
third-party dependency — required by the module under test itself).

```bash
# 1. Materialize the module at the pinned commit.
#    Option A — local worktree from an existing hermes-agent clone:
git -C /path/to/hermes-agent worktree add /tmp/hh-bench-49b044a \
    49b044a322b5a87e4f45fb18e73d09d0b204165e

#    Option B — CI / shallow fetch (no local clone needed):
git clone --filter=blob:none --no-checkout \
    https://github.com/NousResearch/hermes-agent /tmp/hh-bench-49b044a
git -C /tmp/hh-bench-49b044a fetch --depth 1 origin \
    49b044a322b5a87e4f45fb18e73d09d0b204165e
git -C /tmp/hh-bench-49b044a checkout FETCH_HEAD

# 2. Run.
python3 benchmarks/run_benchmarks.py \
    --out results/$(date +%F)-$(uname -s | tr 'A-Z' 'a-z')-$(uname -m) \
    --module-path /tmp/hh-bench-49b044a --check
```

`--module-path` defaults to `/tmp/hh-bench-49b044a`. `--check` exits nonzero
if any recoverable case has fidelity < 100% or any workload errored, so the
suite doubles as a CI gate — with one documented platform exception (next
section).

## Known upstream issue on Windows (measured, not patched)

At the pinned commit, `resolve_spill_capability` opens the ciphertext
without `os.O_BINARY`; on Windows the CRT reads in text mode (CRLF folding,
Ctrl+Z truncation), AEAD verification fails, and same-session recovery
raises `SpillCapabilityError` — it fails **closed** (availability loss;
artifact at rest is intact and verifies byte-exact when read in binary
mode). Evidence and details: `docs/BENCHMARK_REPORT.md` ("Windows
finding").

On Windows the runner therefore reports affected cases as
`KNOWN-ISSUE (payload intact)` instead of `PASS`: `fidelity_exact_bytes`
still records the module's real resolve result (`false`), and the artifact
is verified intact at rest via an explicit `O_BINARY` read using the
module's own key/AAD/filename derivation. `--check` on Windows accepts only
this exact deviation; any other failure, on any platform, fails the check.
No fake pass: POSIX legs report true 100% fidelity, Windows legs report
`known-upstream-issue: 15` (CI run 34076237564, full matrix green).

## Reproduce (continued)

Outputs: `raw_results.json` (machine-readable) and `summary.md` (human).

The runner sets `HERMES_HOME` to a private temp directory for the duration of
the run and deletes it afterward. Spill artifacts (AES-GCM ciphertext) never
touch your real Hermes home and are never committed. Capability URIs are used
in memory only; result files contain no URIs and no absolute paths.

Note: the runner imports the module's private `_write_capability_spillover`
to time the raw spill write in isolation. That is a deliberate research
measurement of exactly this commit, not a supported API.

## Fixtures

All payloads are 100% synthetic, generated by `benchmarks/fixtures.py` from
`random.Random(seed)` with fixed seeds — byte-identical on every machine and
OS. Each workload plants sentinels
(`SENTINEL-<WORKLOAD>-{HEAD,MIDDLE,TAIL}-7f3a9c2e`) so survival and recovery
are mechanically checkable. Session IDs are synthetic
(`bench-session-0001` / `bench-session-9999`).

| workload | generator | nominal size | planted content |
|---|---|---|---|
| `terminal_log` | `terminal_log()` | ~480K chars | head/middle/tail sentinels in a synthetic build log |
| `web_extract` | `web_extract()` | ~320K chars | `PLANTED-FACT` about the fictional Zorblax comet in the omitted middle |
| `repo_search` | `repo_search()` | ~400K chars | sentinels across synthetic `rg`-style match lines |
| `json_output` | `json_output()` | ~440K chars | sentinel-tagged records at head/middle/tail of a JSON array |
| `multi_tool_turn` | `multi_tool_turn()` | 5 × ~120K chars | per-result sentinels; aggregate exceeds every profile's turn budget |

## Profiles

Context windows 32,768 / 131,072 / 1,048,576 tokens. Per-result and per-turn
char budgets are **derived at runtime by the module's own
`budget_for_context_window()`** (`tools/budget_config.py` at the pinned
commit) — the benchmark does not hardcode them. See `docs/PROFILES.md`.

## Cache telemetry schema (offline: N/A)

Provider prompt-cache telemetry requires a live provider API; this benchmark
is fully offline and records the fields as `null` with `available: false`:

```json
"cache_telemetry": {
  "available": false,
  "prompt_cache_hit_tokens": null,
  "prompt_cache_miss_tokens": null,
  "note": "N/A offline: no provider API is called by this benchmark."
}
```

A future online variant should populate `prompt_cache_hit_tokens` /
`prompt_cache_miss_tokens` from provider response usage metadata per
workload run, with `available: true`. No values are fabricated here.

## Interpreter used for the committed run

The committed `results/2026-09-07-macos-arm64/` run used the Hermes Agent
development checkout's virtualenv interpreter (CPython 3.11.15,
`cryptography` 50.0.0), because macOS's system `/usr/bin/python3` is 3.9.6
and the module under test requires Python ≥ 3.10 (`int | float` annotations).
No packages were installed globally.

## Environment facts (committed run)

Recorded in `raw_results.json` under `environment`: OS, kernel, machine, CPU,
Python version/implementation, `cryptography` version, module commit. No
hostnames, usernames, or absolute paths.

## Known limitations

- Characters are a tokenizer-independent proxy for tokens (~4 chars/token,
  the module's own conversion constant), not an exact token count.
- Numbers come from a single machine (Apple M5 Max, macOS 26.6.2) for the
  committed results; CI adds ubuntu/macos/windows legs but measures the
  same synthetic workloads, not a hardware sample. Latency is
  sub-millisecond-to-millisecond scale and will vary with hardware and
  filesystem. Do not generalize any single-workload reduction ratio into a
  universal token-savings claim.
- On Windows, exact-recovery fidelity via the module's own resolve path is
  currently blocked by the documented upstream text-mode read bug (see
  above); the benchmark verifies payload integrity at rest instead.
- Payloads are synthetic and benign; entropy/structure of real tool output
  differs (it affects preview shape, not fidelity).
- No provider cache telemetry (offline); schema reserved above.
- Timing uses `time.perf_counter` medians over 3 reps — enough to show the
  overhead is millisecond-scale, not a statistically rigorous latency study.
